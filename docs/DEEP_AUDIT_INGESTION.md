# Deep audit ingestion: what changed

Before asking whether an analyzer found a defect, CF now has a strict intake
boundary for checking which analyzer, which source bytes and which report the
review is actually about. This is a library-level foundation, not the completed
Deep Defect Mesh decision engine or a new release approval.

## Contract

`verify_deep_audit_plan(path, trust_root_path, trust_root_sha256, workspace_root)`
verifies an external Ed25519 DSSE envelope with payload type
`application/vnd.factory.deep-audit-plan.v1+json` and schema
`factory.deep-audit-plan.v1`. The separately supplied trust pin must match the
exact trust-root bytes. A signature identifies an allowed signer under that
pin; it does not prove that the report was genuinely produced by a scanner.

Required payload fields:

- `schema`, `id`, `issued_at`, `expires_at`: timezone-aware validity, at most 24 hours.
- `sources`: 1–128 `{path, sha256, bytes}` bindings.
- `candidate_sha256`: canonical hash of sources sorted by path.
- `analyzers`: 1–8 `{id, driver, version, report, canary_report}` objects. Each report binding has `path` and `sha256`; paths and hashes are distinct.
- `rules`: 1–256 objects with `id`, `obligation_id`, `category`, `aliases`, `severity`, `max_new`, `max_total`, `min_trace_steps`, `require_source_sink`, `allowed_suppressions`, `origin`, `remediation`, and `consequence`. Each alias names `analyzer_id` and `rule_id`. Only human-confirmed/trusted-source origins authorize rules.
- `canaries`: 1–128 `{id, analyzer_id, rule_id, fingerprint_sha256}` objects referencing approved aliases, with coverage for every analyzer.

The result includes plan, ruleset and canary-set hashes and verified source
bindings. These are input checks only: canary **detection** and threshold
evaluation remain pending. No signing key is generated by the runtime.

## Report normalization

`normalize_sarif(root, binding, analyzer, source_hashes)` checks exact bytes,
SARIF 2.1.0, one declared driver/version, successful invocation flags and error
notifications. It retains result kind, baseline state and suppression state;
none of these labels independently authorizes a pass. Driver rule indices must
agree with explicit rule IDs. Rule default severity is honored.

Native fingerprints supply stable finding identities independent of line
numbers. Source hashes, locations and ordered flow steps supply a separate
trace hash. Moving a finding can preserve identity while changing its trace.
Fingerprint stability depends on the analyzer; CF does not invent missing
fingerprints or claim universal semantic identity across engines or versions.

Primary and flow locations must refer to locally hash-verified sources. No raw
finding messages, snippets or source bodies appear in normalized output.
Suppression records remain visible. Report success is not proof that a scanner
ran, that its configuration is adequate, or that the source has no defects.

## Deliberate subset and limits

Each file is capped at 10 MB (10,000,000 bytes). Duplicate JSON keys, nonfinite
numbers, path escapes, linked files, ambiguous Windows paths, missing native
fingerprints and duplicate finding identities are rejected. Sources are read
again after parsing; this is not an operating-system isolation or atomic
snapshot guarantee.

Expand SARIF URI-base, artifact-index, external-property and tool-extension
indirection upstream. Canonical relative paths are required; encoded paths
need explicit normalization upstream. This is intentionally stricter than
general SARIF ingestion and is **not** a full SARIF conformance validator.

The format choices follow [GitHub's SARIF support documentation](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support),
particularly native fingerprints, rule identifiers, driver metadata and code
flows. These are format references, not claims of executing CodeQL, Semgrep,
Infer or any commercial analyzer during this slice.

## Local verification

- Historical deep-audit-ingestion slice collection (Windows/Python 3.11, 2026-09-03): 1,169 passed, 3 skipped in 192.18 seconds; superseded by the 0.46.2 release-gate total of 1,319 passed, 3 skipped.
- Final focused intake suite: 47 passed, including three tests added after the full-suite collection (signed intake integration, inherited severity and flow-order identity).
- SpecLine: strict validation and 13 requirement mutations passed; three-module drift audit passed.
- ForgeLine: ingestion-scoped review, architecture and smoke passed. Scaffold rejection occurred at import, so it is not claimed as semantic mutation coverage.
- A separate in-memory mutation removed the report/source hash comparison; the tampered-but-valid report test failed as required. No production file was mutated.

Forge's architecture CLI labels its operator approval as human; this execution
was by the assistant under the user's implementation request, not independent
human review or release approval. Test signatures use temporary fixture keys.
